# Netlify deployment

## Repository and build

Import `D-GENIUSES/SCHOLAU` from GitHub. Select `staging` as the production
branch for the test site: this gives it the stable primary `*.netlify.app`
address rather than an ephemeral branch URL. Set package directory to
`apps/web` and leave base directory unset (repository root). The root
`netlify.toml` sets the build command and publish directory. Do not set the
base to `apps/web`: workspace dependencies must install from the root.

Node.js 24 and pnpm 12.11.2 are pinned. Install with the frozen lockfile.
Netlify automatically supplies its current Next.js adapter; do not use a
static export or a catch-all SPA rewrite. Confirm the adapter appears in
the deploy log and packages the Next.js server functions successfully.

In Branches and deploy contexts, disable Deploy Previews and additional
branch deploys. The config also skips those build contexts. The Netlify
production context belongs to `staging` until the public launch.

## Environment

Add values through Netlify's environment settings for the production
deploy context. Never place credentials in `netlify.toml`, GitHub source,
build commands, or logs. Do not copy local `.env` files into the deploy.

On the free plan, use standard environment variables in the production
context with all scopes. Netlify requires an upgraded plan for specific
scopes, and protected secret values cannot use all scopes. The application
still restricts private credentials to server code. On a plan that supports
scopes, restrict the variables below to Builds and Functions and mark the
Supabase server key and R2 credential pair as secret values.

| Variable | Scope | Value/source |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | Builds and Functions | Existing hosted Supabase URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Builds and Functions | Same project's publishable/anon key |
| `NEXT_PUBLIC_APP_BUILD` | Builds and Functions | Compatible integer build number, initially `1` |
| `NEXT_PUBLIC_SITE_URL` | Builds and Functions | Stable HTTPS Netlify origin, no trailing slash |
| `SUPABASE_SECRET_KEY` | Builds and Functions | Existing server-only Supabase secret |
| `LESSON_ASSET_STORAGE` | Builds and Functions | `r2` |
| `R2_ACCOUNT_ID` | Builds and Functions | Existing Cloudflare account ID |
| `R2_BUCKET` | Builds and Functions | Existing private `scholau-assets` bucket |
| `R2_ACCESS_KEY_ID` | Builds and Functions | Bucket-scoped object credential |
| `R2_SECRET_ACCESS_KEY` | Builds and Functions | Matching private object credential |

The admin users page reads the server credential while rendering. Set
the complete configuration before the first deployment. The supported
`SUPABASE_SERVICE_ROLE_KEY` fallback is unnecessary when the preferred
secret is configured. Only the four `NEXT_PUBLIC_` variables may appear
in browser bundles. Redeploy after changing environment values.

## Connected services

In hosted Supabase Authentication URL Configuration, set Site URL to the
stable Netlify origin and add `<origin>/auth/callback` and
`<origin>/auth/callback?next=/**` to the redirect allowlist. Preserve existing
localhost callback entries. Verify the actual confirmation and recovery
links generated by the app; do not allow all Netlify projects with a broad
wildcard. Local `supabase/config.toml` does not update hosted auth settings.

Confirm `20261017000800_r2_lesson_asset_access.sql` is already applied and
repeat the read-only lesson-asset inventory before enabling R2. Existing
migration scripts support inventory and verified copying; never reset the
hosted database or replay historical migrations during web deployment.
R2 remains private. Uploads proxy through Next.js and reads use signed
URLs, so browser bucket CORS and a public bucket are unnecessary.

The `push-delivery` function stays hosted in Supabase. Its VAPID private
key, scheduler secret and Vault entries must not be copied to Netlify.
The worker accepts scheduler-authenticated POST requests; it has no web
origin allowlist. The browser fetches public push configuration through
the existing RPCs. Verify `/push-sw.js` is served without caching and
with `Service-Worker-Allowed: /`. Push subscriptions are origin-specific;
users must enable notifications again after moving to the custom domain.

## Release gates

Record the deployed commit and date with each result; earlier local
verification reports do not establish that the Netlify site works.

- Run workspace lint, type checking and production build with Node 24.
- Confirm the deployed adapter, environment availability and error-free
  function startup; check public pages and protected-route redirects.
- With designated accounts, verify signup/email confirmation, recovery,
  login/logout and session persistence across navigation and reloads.
- Verify course access, lessons, assessment submission, battle realtime,
  admin user creation and profile-photo upload/display.
- Verify authorized R2 upload and signed delivery, plus anonymous and
  unenrolled access denial. Check that the bucket still denies public reads.
- Enable browser notification permission through the normal UI; verify
  subscription, worker delivery and notification deep-link handling on HTTPS.
- Check browser JavaScript for actual private credential values using a
  local scan that reports only pass/fail, never the credentials themselves.
- Inspect Netlify function errors and Supabase push health without logging
  user payloads or secrets. Keep production readiness pending until all
  authenticated checks pass.

## scholau.com cutover and rollback

After the test release passes, merge it to `main` and change Netlify's
production branch to `main`. Add `scholau.com` and `www.scholau.com` to the
same Netlify project. Apply the exact DNS targets Netlify provides, wait
for HTTPS, and choose the apex as primary so `www` redirects to it.

Update `NEXT_PUBLIC_SITE_URL`, the hosted Supabase Site URL and callback
allowlist, rebuild, and repeat auth, uploads and push checks. Preserve
the Netlify callback temporarily while in-flight confirmation links are
still valid. No domain or DNS change is needed for the initial test site.

Roll back the web release by publishing the previous successful Netlify
deploy. Database migrations and settings do not roll back with it.
Changing R2 back to Supabase requires copying any R2-only assets back
first; see [R2 operations](r2-storage.md). Keep the existing push delivery
kill switch available for operational incidents.
